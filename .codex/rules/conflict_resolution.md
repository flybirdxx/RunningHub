# RunningHub 冲突裁决框架

更新时间：2026-06-27

## 1. 优先级

当规则冲突时，按以下顺序裁决：

1. 用户当前明确指令。
2. 系统/开发者安全规则。
3. 根 `AGENTS.md` 与 `.codex/rules/project_rule.md`。
4. 目标目录最近的局部 `AGENTS.md`。
5. `ARCHITECTURE.md`、`DEVELOPMENT.md`、`docs/governance/` 与 `docs/migration/`。
6. 历史聊天记录和未写入仓库的记忆。

## 2. 常见冲突处理

- 局部规则允许、根规则禁止：以根规则为准，除非用户明确要求并接受风险。
- 文档旧、源码新：先用源码和 Gradle 配置验证，再更新文档，不把旧文档当当前事实。
- 架构需要与快速修复冲突：小修可落在现有边界内；跨模块行为变更必须同步更新测试和文档。
- Android 和 iOS 约束冲突：`commonMain` 保持平台无关，差异进入 `androidMain` / `iosMain`。
- 自动化验证与人工证据冲突：自动化只能证明本地可执行部分，外部 CI、商店、签名、真机权限以人工证据为准。
- CodeGraph 与磁盘文件不一致：以当前磁盘文件为准，并运行 `codegraph sync` 或 `codegraph status` 复核。

## 3. 缺失信息

- 能用合理假设推进时直接执行，并在交付中说明假设。
- 缺失信息会导致破坏性操作、敏感数据修改、外部发布或大范围架构偏移时，先询问用户。
- 无法验证时不得声称完成，只能说明已完成部分、未验证部分和下一步。
